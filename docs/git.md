# Git — branches, tags and commits

## One repository, three roots

`api/`, `web/` and `android/` live in this one repository; their internal
shape is in `docs/architecture.md`. There are no submodules and no
per-root git history — one `git log` covers all three.

## Branches

- **`main`** — always green, always deployable in principle. Nothing is
  pushed straight to `main` except the merge commit that closes a sprint.
- **`sprint-N`** — cut from `main` at the start of sprint N. Every story
  branch for sprint N is cut from `sprint-N` and merged back into it. At
  the end of the sprint, `sprint-N` is merged into `main` and tagged
  (see **Tags**). The list of sprints and their point budgets is in
  `docs/blocks.md`.
- **`<ID>-<slug>`** — a story branch, e.g. `CRM-16-repo-conventions`. Cut
  from the current sprint branch, merged back into it, and **deleted on
  merge**, both locally (`git branch -d`) and on the remote
  (`git push origin --delete`). Automated pruning of merged branches is
  out of scope here; it is enforced by convention until CI (CRM-28) adds
  it.

The `<ID>` is the tracker key exactly as the tracker prints it —
`CRM-16`, not `crm-16`. Git branch names are case-sensitive on Linux and
case-insensitive on macOS; mixing the casing across sprints breaks the
first cross-platform checkout.

The `<slug>` is the story's kebab-case slug from its id (the last field of
`FEATURE-N-LAYER-<slug>`), using the feature names in `docs/taxonomy.md`
and no abbreviation of them.

## Tags

One tag per closed sprint, named `sprint-N`, placed on the commit that
merges `sprint-N` into `main`. The tags are the record of what shipped and
when; nothing else declares it. A later change to the branch model edits
this file — it does not invalidate a tag already placed.

## Commit style

- **Subject** — imperative, present tense, no trailing period, ≤ 72
  characters. Says *what changed*: `add root README`, not `added` or
  `README stuff`.
- **Body** — separated from the subject by a blank line, wrapped at 72
  columns. Says *why* this change was made and *what alternative was
  rejected*. Every non-trivial commit has a body; a one-line commit is
  only for a change whose reason is fully visible in the diff.
- **No AI attribution.** A commit must not credit an automated assistant
  or tool in any form — no co-author trailer for one, no "generated by"
  line, no tool emoji, no such note anywhere in the subject or body. If
  one slips in, remove it with `git commit --amend` (last commit) or
  `git rebase -i <ref>` (older commits) **before** the branch is pushed
  for review — not after. This file states the rule but never spells out
  an example trailer: a repo-wide grep for one must not match here.

### Known deviation

Rewriting history on `main` to scrub an attribution from an older shared
commit is **not** done — it would rewrite the `.squad/` and `docs/`
commits everyone has already pulled. The rule is enforced strictly for
every commit from `CRM-16-repo-conventions` onward. A bad commit that
reaches `main` is fixed forward with a new commit; `main` is never
force-pushed.

## A worked example

A story branch reads as a sequence of decisions, one per commit:

```
docs: add root README naming the three roots and the planning system

    The repo had no root README. The new one describes only what exists
    today and points at docs/ rather than restating it. Rejected a README
    that also sketched the roadmap: it duplicates docs/blocks.md and goes
    stale the first time the plan changes.

chore: track empty api/, web/, android/ with .gitkeep

    The roots existed on disk but carried no tracked file, so a fresh
    clone did not show them. Chose .gitkeep over a per-root README, which
    would restate the root README three times and be ignored by /*.md
    anyway.

docs(git): document sprint and story branch model, commit style

    New contributors had no written source for branch names, tag format
    or commit style. Rejected folding this into the root README: the
    README is the front door and stays short; the mechanics belong in
    docs/.
```

Each subject says what changed; each body says why, and what was turned
down. `git log` on the branch is then a record, not a pile of `wip`.
